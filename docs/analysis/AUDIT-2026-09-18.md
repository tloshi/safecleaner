# ViggoClean 0.2.0 — Final Assessment

## Verdict

As engineering, this is roughly **8/10 against solo-developer macOS utilities** — Swift 6 clean with zero unsafe escape hatches, one destructive call in the whole codebase (`FileSafety.swift:94`, `trashItem`), and a safety test suite that asserts files *survive* failure rather than that an error was returned (`SafetyTests.swift:74-81`). As a product it is about **3/10**: on your own 512 GB Mac it offers ~1.83 GB while the 8.2 GB DerivedData it advertises first (`README.md:32`) is refused by your own safety policy, and eight shell commands you already know recover 80-120 GB. **Overall: 5/10** — an unusually well-built engine that is not yet connected to the wheels. The good news is that you did the expensive, hard-to-retrofit half first.

Can it go in a store? Not the Mac App Store as designed, and not anywhere at all today — `spctl -a -vvv -t exec build/ViggoClean.app` returns **rejected**, so even your friends cannot open it. Developer ID + notarized DMG is the realistic channel, and you are closer to it than the audit's own estimate: you already hold an active paid Apple membership.

## What this project does unusually well

**Permanent deletion is structurally impossible, not merely avoided.** There is exactly one destructive filesystem call — `FileManager.default.trashItem` at `FileSafety.swift:94`. No `removeItem`, no shell, no root helper. `SafetyTests.swift:74-81` proves the no-fallback property: when the trash operation throws, the test asserts `FileManager.default.fileExists(atPath: url.path)`. Most shipping Mac cleaners call `rm -rf` on cache paths directly.

**The containment logic is correct in the ways that actually matter.** `isInside` (`FileSafety.swift:6-9`) is component-wise on `standardized`, not a string prefix, and `../secret` is tested (`SafetyTests.swift:35`). `validate` (`:14-28`) walks every ancestor with `attributesOfItem`, which is lstat-based, so a symlinked ancestor causes refusal instead of authorising its target — with a comment at `:12-13` explaining exactly why. The scan-to-cleanup race is closed by re-snapshot and digest compare at `FileSafety.swift:103-106`.

**The tests attack the code.** `SafetyTests.swift:64-73` replaces the candidate directory with a symlink between scan and cleanup and asserts the trash closure was never called. That is a race most commercial cleaners would fail, and testing the *absence* of destruction is the only assertion shape that protects anyone.

**There is no Select All anywhere.** `ViewState.swift:23-25` and `ReviewView.swift` have no bulk-selection verb. Pre-checked Select All plus a big green button is where real-world cleaner accidents come from. The friction is the safety feature.

**Swift 6 clean with no escape hatches.** The package compiles under `swiftLanguageMode(.v6)` and `-strict-concurrency=complete` with zero warnings. Across 2,419 lines there is not one `try!`, `as!`, force unwrap, `fatalError`, `@unchecked Sendable`, `nonisolated(unsafe)`, `DispatchQueue` or semaphore. Cancellation genuinely propagates into the detached scanner worker (`FileSystemServices.swift:8-15`) at ~1 ms latency.

**It refuses to lie about its own numbers.** `ReviewView.swift:156`: "Moving to Trash does not immediately free disk space. No permanent deletion is performed." Four separate places say this. Every mainstream competitor headlines an inflated "GB freed" the instant files move. The confirmation sheet (`ReviewView.swift:129-165`) lists every full monospaced path, requires an acknowledgement toggle (`:153-155`), and deliberately gives the destructive button no `.defaultAction` keyboard shortcut while Cancel gets `.cancelAction` (`:159-161`).

**`docs/VALIDATION.md:37-45` documents per version what was *not* tested.** I have not seen a commercial product do that.

## What is actually wrong

Ordered by how much it matters. A note on calibration first: the raw audit produced 7 "confirmed" + 12 "unverified" + 45 minor findings, but several are the same defect under different lenses (the DerivedData refusal appears twice; sandbox three times; LICENSE, signing and history.json twice each). The real defect count is roughly a third lower than it reads, and almost every finding is about **reach and release plumbing**, not code quality.

**1. Ad-hoc signing — the only thing that is broken for you right now.** `scripts/build-app.sh:13` runs `codesign --force --sign - --options runtime`. Verified: `flags=0x10002(adhoc,runtime)`, `TeamIdentifier=not set`, `Internal requirements count=0`, and `spctl -a` returns **rejected**. Two consequences. A friend who receives the app with a quarantine xattr gets "cannot be opened"; on macOS 15+ the right-click-Open bypass is gone. And because the designated requirement falls back to a bare cdhash, every rebuild is a new app identity, so any Full Disk Access grant silently dies and the next scan quietly finds less with no error. These are one fix, not two. *Partially disclosed* — `ROADMAP.md:155` scopes Developer ID signing as conditional future work, but nothing records that the current state is Gatekeeper-blocked. Effort: an afternoon.

**2. The whole-tree package/symlink rejection kills the flagship feature.** `FileSafety.swift:45-47` (link/special), `:51-53` (package) and `:58-60` (hard link) abort the *entire* candidate on the first offending entry. On your machine that refuses DerivedData (8.2 GB, 181 symlinks, 458 `.framework`/`.bundle`/`.app` dirs), `~/Library/Caches/Google` (6.3 GB), JetBrains (1.5 GB), Spotify (1.3 GB) and SwiftPM (929 MB). 91% of the bytes your own rules nominated are discarded by your own policy, and it shows up in the UI as a "skipped location". Note the asymmetry: the *ancestor* check in `validate` is load-bearing; the *descendant* symlink check guards a threat `trashItem` does not have, since a rename-based move never dereferences links inside the moved tree — your own `SafetyTests.swift:42` asserts `secret.txt` survives, which it would have anyway. *Disclosed as a policy* in `ARCHITECTURE.md`; **not disclosed** is that it means DerivedData never works. Effort: see the caveat under "What I would do next" — not the "hours" the audit claims.

**3. The SwiftPM rule can never fire on any Mac, and this was nearly lost.** `~/Library/Caches/org.swift.swiftpm` has `pathExtension == "swiftpm"`, a LaunchServices-registered package type, so `isPackage == true` for the candidate **root itself**. `snapshot` calls `walk(url)` → `record(url)` (`FileSafety.swift:82, 74`), which throws at `:51-53` before touching a single child. The rule at `Scanner.swift:62` is dead by construction. Worse, `"org.swift.swiftpm"` is also in the `reserved` list at `Scanner.swift:79`, so the generic Library/Caches loop skips it too — 929 MB invisible twice by two independent mechanisms. **Undisclosed.** This is the cleanest one-line-fixable bug in the repo, and it needs a root-level exemption, not a policy change. Effort: minutes.

**4. No diagnosability at all.** Zero logging statements in the entire source tree (verified by grep: 0 hits for `os.Logger`, `OSLog`, `NSLog`, `print(`). Every error is flattened to `localizedDescription` (`FileSafety.swift:115`, plus ~15 sites across Scanner, repository and ViewModel), so the app structurally cannot distinguish "macOS denied permission" from "the file changed" — the single most useful thing a disk cleaner can say. No support contact (`WorkspaceScreens.swift:121`), no diagnostics export, no update mechanism. Your no-telemetry stance is right; it has quietly become no-diagnosability. **Undisclosed.** Effort: days.

**5. `history.json` has no schema version and fails closed permanently.** `LocalCleaningRepository.swift:30-31` sets `historyAvailable = false` on any decode error, and `:74-75` then refuses all cleanup. `CleanupRecord` (`Models.swift:85-96`) has no version field, and there is no in-app recovery — the user must hand-delete `~/Library/Application Support/ViggoClean/history.json`. Shipping 0.3 with any model change bricks the Clean button for every 0.2 user. The fail-closed choice is *disclosed and correct* (`ARCHITECTURE.md:31`); the absence of a recovery path is **undisclosed**. Effort: hours. Related and unflagged: `:104` re-encodes and atomically rewrites the entire history array after **every single item**, with no cap on history length.

**6. No LICENSE, no warranty disclaimer anywhere.** `ls LICENSE*` returns nothing; grep for `warranty|disclaim|liab` across the repo returns nothing. For a tool that moves other people's files to Trash, this is the cheapest serious gap you have. **Undisclosed.** Effort: ten minutes.

**7. Missing store-submission artifacts nobody in the audit caught.** There is no `PrivacyInfo.xcprivacy` anywhere (`find` returns 0), yet you call required-reason APIs: `attributesOfFileSystem` (`FileSystemServices.swift:29`), `attributesOfItem` (`FileSafety.swift:43`) and `UserDefaults` (`PersistenceServices.swift:11-16`). A privacy manifest is mandatory for any App Store submission. Separately, `build/ViggoClean.app` contains exactly four files and **no `Assets.car`** — the SwiftPM build path (`build-app.sh:7-11`) copies only the executable, Info.plist and `.icns`, and `Info.plist:9-10` uses legacy `CFBundleIconFile` with no `CFBundleIconName`. App Store Connect rejects that. Also missing: `LSApplicationCategoryType`, and any TCC usage-description keys even though `MacDesktopService` invites users to add Desktop/Documents/Downloads folders.

**8. Arm64-only binary.** `build-app.sh:4` runs `swift build -c release` with no `--arch` flags; `lipo -info` confirms `Non-fat file: architecture: arm64`. `Info.plist:21` promises macOS 14.0+, which reads as "any Sonoma Mac". A friend on an Intel MacBook gets a bundle that cannot launch. **Undisclosed.** Effort: one flag.

**9. `SWIFT_VERSION = "5.0"` in both Xcode configurations** (`project.pbxproj:63, 65`), the shared scheme has **no `TestAction`** (⌘U runs nothing), and there is no CI. Nothing preserves the Swift 6 cleanliness the code currently has.

### Contested and unverified

**The memory finding is half right.** `FileSafety.swift:73-81` has no `autoreleasepool` and peak growth is real and reproducible (~12.5 KB/entry on a 50k tree; 2,555 MB on 200k; a one-line per-child `autoreleasepool` drops that to 25.8 MB and is *faster*). But two claimed impacts were **refuted by measurement**: memory *is* released at the detached-task boundary (`FileSystemServices.swift:8-10`), and the headline "500k-entry DerivedData → 9 GB" scenario cannot occur, because `record` refuses DerivedData in the first few milliseconds — the real snapshot peaked at 21 MB RSS. Fix it (one line, strictly faster), but it is not the crisis it was filed as.

**The O(n²) dedup at `Scanner.swift:46` was filed as a shipping blocker; I do not agree.** 87 s at 5,000 candidates is real, but your machine has ~120 old logs. MEDIUM, not blocking.

**Never verified by anyone:** the VoiceOver findings (the Review list is ~1,100 ungrouped stops, no announcements after a cleanup), the accessibility/Dynamic Type findings, and the claim that the ViewModel test coverage is good — it was counted, never read.

## The efficacy problem

Direct answer: **no, it does not currently solve your problem.**

Measured on this machine (460 GiB volume, ~350 GiB used, 81-84% full), the real scanner offers **1.83-1.89 GB** — about 0.5% of used disk. Of your seven developer rules (`Scanner.swift:60-68`), four refuse and three point at paths that do not exist here, delivering ~563 MB combined.

What is actually sitting on the disk, measured with `du`: 39 GB `/Library/Developer/CoreSimulator` runtimes, 34 GB `~/.android`, 26 GB Docker VM, 26 GB `/opt/homebrew`, 22 GB `~/Library/Android`, 12.1 GB node_modules, 9.9 GB `~/.gradle` (your rule reaches 494 MB of it), 8.2 GB DerivedData, 6.4 GB CoreSimulator devices, 5.6 GB iOS DeviceSupport. Roughly 200 GB addressable.

Three structural reasons the gap is this wide, beyond the package/symlink policy:
- Scanning is confined to `$HOME` (`Scanner.swift:7, 20`), so the two largest items are invisible by construction.
- `node_modules` is deliberately pruned from project traversal (`Scanner.swift:157`).
- The rule catalogue is seven hardcoded `(String, String, String?)` tuples inlined in a 145-line function. Free competitors ship 30-39 scanners.

Fixing the package/symlink policy unlocks roughly 17 GB immediately. That is a 10x improvement and still an order of magnitude short of what a shell session gets you. The rule-coverage work is months, not hours.

## App Store reality

**Mac App Store: closed, for reasons that are product-shaped, not budget-shaped.** `ENABLE_APP_SANDBOX = "NO"` at `project.pbxproj:64` and `:66` is a deliberate, correct choice, not an omission. The concrete failure mode, measured with signed probe apps: under the sandbox, `FileManager.default.homeDirectoryForCurrentUser` returns `~/Library/Containers/<bundleid>/Data`, so `Scanner.swift:7` and `AppContainer.swift:12` would scan an empty folder the app created itself and report **zero candidates and zero errors** — a confident, silent "your Mac is clean". That is the worst failure mode a cleaner can have.

One audit claim needs correcting: "a sandboxed app cannot read other apps' `~/Library/Caches` at all" is too strong. A probe signed with `temporary-exception.files.home-relative-path.read-write` read the real paths fine. The sandbox forbids reading them *without an explicit grant of that subtree*; security-scoped bookmarks grant the same thing legitimately. `NSWorkspace.runningApplications` and real volume capacity also survive sandboxing. So MAS is technically reachable — it is just the wrong trade: the temporary-exception route is exactly what App Review has refused for a decade, and the bookmark route means rewriting persistence (`PersistenceServices.swift:11-16` stores bare path strings, which are inert on relaunch under sandbox) plus a grant-onboarding flow where two of your seven rules point at dotfolders NSOpenPanel hides by default.

Precedent cuts both ways. DevCleaner for Xcode is free on the MAS, sandboxed, minOS 14.0, and its store copy pitches "especially important if you have relatively small SSD drive" — your sentence, at $0, since 2018. But it survives because it is framed as an *Xcode developer tool*, not a Mac cleaner, and it had to **remove** its UI Previews feature because sandbox permissions could not reach those files. DaisyDisk's store build ships without scan-as-administrator for the same reason. (One judge flagged that the DevCleaner listing could not be re-verified this session — treat it as recalled precedent.)

**Recommended channel: Developer ID + notarized, stapled DMG.** Not MAS, not now. Setapp Desktop is the one "store" that fits a non-sandboxed utility and takes 10-15%, but it wants a mature differentiated app; it is not where this goes next.

**Where the three commercial judges disagreed.** All three converged on the channel; they split on money and on cost. The release engineer verified `security find-identity -v` and found a valid **Apple Distribution: Taulant Loshi (F3X3EF7L5N)** certificate — you already hold an active paid membership, so the "$99 enrollment" in the audit and in the monetization judge's verdict is **wrong**; what is missing is a free Developer ID Application certificate, five minutes from an account that already qualifies. The monetization judge argued for permanently free and open-source (differentiator is auditability, which only works in public; free competitors already claim your exact safety language in their marketing copy). The skeptical user agreed on free but framed it as "not yet good enough to charge", leaving the door open. They also split on effort for the `FileSafety` fix: the audit said hours, the skeptical user said a couple of weekends and warned that rushing it is how you destroy the one thing this project has. I side with the latter.

## If you want to ship this

### (A) Minimum to give it to friends safely

Ordered by dependency.

1. **LICENSE with a warranty disclaimer** at the repo root — 10 minutes. Do this before the next `.dmg` leaves your machine.
2. **SwiftPM root-package exemption** (`Scanner.swift:62` + remove `"org.swift.swiftpm"` from `reserved` at `:79`) — 30 minutes, 929 MB.
3. **A realistic cache fixture**: one tree with a `.framework` directory, one interior symlink, one hard link, a nested excluded path — half a day. This is the precondition for item 4 being verifiable rather than hopeful.
4. **Per-entry package/symlink handling in `FileSafety.record`** (`:45-53`), dropping the descendant-symlink rule and keeping the ancestor check in `validate` — 1-2 weekends including fixtures. See the caveat in the next section.
5. **Developer ID Application certificate, then `build-app.sh:13` → `--sign "Developer ID Application: Taulant Loshi (F3X3EF7L5N)" --timestamp`, plus `--arch arm64 --arch x86_64` on line 4, then `notarytool submit --wait` and `stapler staple`** — one afternoon. Notarize the DMG and staple the DMG; verify with `spctl -a -vvv -t install`. Your bundle is 4 files and 2.5 MB with zero third-party frameworks; it will pass first try.
6. **Schema version on `CleanupRecord`** (`Models.swift:85-96`) + a "Reset activity history" button in Settings — half a day. Must land before any 0.3.
7. **`os.Logger` at `FileSafety.swift:113-116` and `LocalCleaningRepository.swift:96-110`, plus typed errors instead of `localizedDescription`** — 1-2 days.
8. **Three TCC usage-description keys in Info.plist** and a Full Disk Access explainer with an `x-apple.systempreferences:` deep link — half a day.
9. **One-line `autoreleasepool` in `walk`** (`FileSafety.swift:79`) — 15 minutes, and it makes scans faster.

Realistic total: 4-6 weeks at 8-10 hours a week.

### (B) Additional work to sell it to strangers

1. **Extract the rule catalogue** out of the 145-line `scan` function into a versioned, per-rule structure with its own reason and consequence strings — 3-5 days. `ROADMAP.md` Phase 2 cannot land on the current tuple array.
2. **Rules that reach the real bytes**: CoreSimulator runtimes and devices, iOS DeviceSupport, Xcode Archives, subdirectory-aware `~/.gradle`, Android SDK/AVD, a Docker adapter that talks to the daemon rather than deleting a 26 GB VM file, Homebrew via `brew --cache` — 6-10 weeks with fixtures per rule as `AGENTS.md:11` requires.

4. **Replace the card list with a real `Table`** (`ReviewView.swift:51-56`): sortable columns, native multi-select and shift-click range, while keeping your deliberate no-Select-All stance — 1 week. Highest-leverage single change for making it read as a Mac app.

6. **Update channel** (Sparkle or a dumb hosted JSON version check) — 3-5 days. Without it you cannot push a safety fix to anyone who already installed.
7. **CI + a `TestAction` in the shared scheme + `SWIFT_VERSION = 6.0`** — 1 day.
8. **Distinguish failure from success in the UI** (`ContentView.swift:23-32` renders "Scan failed" in the same mint info banner as "12 items moved to Trash") — half a day.
9. Only if pursuing MAS: security-scoped bookmark persistence, entitlements file, `PrivacyInfo.xcprivacy`, asset-catalog icon with `CFBundleIconName`, `LSApplicationCategoryType`, review notes declaring the `--preview-data` flag — 2-3 months, for a deliberately worse product.

## What I would do next

**1. Reframe `FileSafety.snapshot` before you touch it.** Every top finding falls out of one conflation: the function both *measures* a tree and *authorizes* it. Loosening `record` from `throw` to `return` is not a pure relaxation — once the snapshot skips packages and symlinks, `TreeStamp` no longer describes what `trashItem` actually moves at `FileSafety.swift:110`. The estimate under-reports, and a `.framework` inside DerivedData gets trashed even though it was deliberately excluded from validation. Write down that the *moved* unit is the whole directory and the *measured* unit is a subset, correct `ARCHITECTURE.md` where it currently promises the opposite, then build the realistic fixture, *then* change the code. Note that `walk` will need an explicit "do not descend" signal for packages (a package is still `typeDirectory`), while symlinks self-solve because `attributesOfItem` is lstat-based. Do the SwiftPM root exemption separately in the same session — it is one line for 929 MB.

**2. Sign it properly and give it a licence.** One afternoon, and it fixes Gatekeeper and the TCC-reset problem simultaneously. The membership is already paid; you need a free Developer ID Application certificate, `--timestamp`, `--arch arm64 --arch x86_64`, notarytool, stapler, and a LICENSE file. Right now your friends cannot open the app at all, and on an Intel Mac they never will.

**3. Make failures visible, then publish the source.** `os.Logger`, typed errors instead of `localizedDescription`, a diagnostics export, a contact address, and a version check. Then put it on GitHub under MIT or Apache-2.0 — not Apache + Commons Clause, which is the licence that helped strand Pearcleaner. Your differentiator is that the safety claims are *checkable*: one `trashItem` call, no Select All, a test that proves the file survives a failed delete. That is a real position in the most trust-hostile category on the platform, and it is worth exactly nothing from an unknown developer shipping a closed binary. Publishing the repo is the marketing.

Do not price it yet. Charging $29 for 1.83 GB would burn the only asset this project actually has.
